## Findings

### 1. MEDIUM: the sender check compares strings from two different URL canonicalizers, so a valid page can be rejected
Where: ARCHITECTURE > IPC contract > Bridge, step 1 ("`rendererUrl` is the URL the window loads, so the two cannot drift").
Problem: `rendererUrl` is a WHATWG `href` built by Node (`pathToFileURL` + `new URL`). `e.senderFrame.url` is Chromium's canonical GURL spec of the page it actually loaded. The two canonicalizers do not produce identical strings for every Windows path. The known case is the drive letter: Chromium's Windows file-URL canonicalizer uppercases it (`file:///c:/…` → `file:///C:/…`), while WHATWG and `pathToFileURL` keep it as given. `indexHtml` derives from the main bundle path, which follows `process.execPath`, which keeps the case the exe was launched with. A user-typed install folder (`allowToChangeInstallationDirectory: true`, e.g. `d:\apps\TeleFlow`), a lowercase command line, or a Run entry written from such a launch then gives a lowercase drive in `rendererUrl` and an uppercase one in the frame URL. Every call returns 403, including `auth.get`, so the app is unusable for that install. The packaged smoke test cannot catch it because it launches `release\win-unpacked` with the build machine's path. The percent-encode sets of the two canonicalizers may also differ for rarer path characters (braces, backtick, `^`); I have not checked those. An invalid frame URL (`new URL` throws) would also surface as a 500 instead of a 403.
Fix: keep a full-page comparison (never origins), but compare `file:` pages as decoded, case-folded paths (NTFS is case-insensitive) so the canonicalizers cannot disagree, and reject on any parse error:
```ts
// pure, so it can be tested under node:test (core/storage.ts, next to resolvePaths)
export const pageKey = (s: string) => {
  const u = new URL(s); u.hash = ''; u.search = ''
  return (u.protocol === 'file:' ? fileURLToPath(u) : u.href).toLowerCase()
}
// electron/main.ts
const rendererUrl = (!app.isPackaged && process.env.ELECTRON_RENDERER_URL) || pathToFileURL(indexHtml).href // win.loadURL(rendererUrl)
const rendererKey = pageKey(rendererUrl)
// in ipcMain.handle('call', (e, req) => …)
let key: string | null = null
try { key = e.senderFrame ? pageKey(e.senderFrame.url) : null } catch {}  // bad URL or encoded slash → reject
if (key !== rendererKey) return { ok: false, status: 403, error: 'Not allowed' }
```
Add to the unit list: `pageKey('file:///C:/X/out/renderer/index.html#/queue') === pageKey(pathToFileURL('c:\\x\\out\\renderer\\index.html').href)`; a sibling file (`…/renderer/other.html`) differs; `http://localhost:5173/#/a` equals `http://localhost:5173`. Update the Security IPC bullet wording to "full page path (file) or URL (dev), hash and query stripped, case-insensitive".

### 2. MEDIUM: after a crash, an active upload with no pending id left is never settled and stays "Uploading" forever
Where: ARCHITECTURE > Upload steps 4 and 6; Client lifecycle ("the next `ready` rebuilds the routing map from `files[].pendingId` and runs the check of Upload step 6"); call map row "Upload crash recovery".
Problem: recovery is driven only by pending ids: the routing map is rebuilt from `files[i].pendingId`, and on `ready` each still-unsettled pending id gets `getMessage`. The job-level outcome ("When no file of the job has a `pendingId` left: …", step 4) runs when a file settles. An upload row left `active` by a crash with no pending id therefore gets no event and no check:
- a crash during step 2 (the hard-link/copy to `tmp\<jobId>` with "Keep original file names" off, which takes many seconds for a multi-GB file on another volume);
- a crash between TDLib accepting `sendMessage` and `files` being persisted;
- a crash between the last file settling and the job update.

`requeueActiveDownloads()` covers downloads only and the pump starts only `queued` rows. The row stays `active` with no live state: "Uploading" pill, zero speed, counted in the Queue badge and `live.counts`, and its files are never posted unless the user happens to pause/resume or cancel. Depending on how the pump computes free slots (unspecified), it may also hold the only upload slot (`maxUploads` default 1).
Fix: add one rule to Upload step 6 and the call map row:
> On `ready`, after the `getMessage` checks are issued, every `active` upload with no `pendingId` left settles at once through step 4: all files have `messageId` → `completed`; otherwise `settleUpload(job)` and fail "Interrupted. Check the chat before retrying" (not retryable, the same rule as vanished pending ids, because TDLib may have accepted a send whose id was never persisted).

Extend the `settleUpload` test: an `active` upload with no `pendingId` and one file without `messageId`, after a simulated restart and `ready`, ends `failed` with that error, not `active`.

### 3. NIT: a scan that ends on an error restarts on every refetch
Where: ARCHITECTURE > Media index scan ("once more on each `scan.state` change (start, finish)"; "Flood waits sleep and continue. A scan stops when the client leaves `ready`").
Problem: errors other than flood waits are unspecified. The natural implementation ends the scan in a `finally` that sets the state back and emits `media:<chatId>`. The open Files View refetches, `chats.media` sees `complete = 0` (or `newest_id < last_message.id`) and starts the scan again, which fails again: about one TDLib call per second plus a refetch for as long as the view is open (for example a channel that became private while selected). The emit-on-finish was added by the round-3 fix, so this path is new.
Fix: one sentence in Media index scan: "A page that fails with anything but a flood wait ends the scan (logged at warn) and adds the chat to an in-memory `failed` set, cleared together with `current`; `chats.media` does not start a scan for a chat in `failed`, and `scan.state` reads `idle`."

### 4. NIT: cancel cleanup also fires TDLib calls for completed rows
Where: ARCHITECTURE > Methods notes (`jobs.action cancel` cleanup: "non-live downloads that ever transferred (`attempts > 0 OR done > 0`)").
Problem: Queue "Remove" on a completed row and Clear All (`cancel` = every job row) delete completed downloads too, and those all have `attempts > 0`. Their TDLib copy was already removed at finalize (or never existed for skip-existing), so Clear All over a long history issues up to 100 `getMessages` calls per 10 000 rows and a `deleteFile` per row for nothing.
Fix: select only unfinished downloads for the cleanup: `kind = 'download' AND status <> 'completed' AND (attempts > 0 OR done > 0)`.
