## Findings

### 1. MEDIUM: the IPC sender check, as written, never matches the packaged renderer
Where: ARCHITECTURE > IPC contract > Bridge, step 1. The text says "`origin + pathname` of `new URL(event.senderFrame.url)` equals the app's renderer URL (dev server URL in dev, the packaged `index.html` file URL otherwise)".
Problem: under WHATWG URL rules, a `file:` URL has an opaque origin. I checked this with Node 24:
- `new URL('file:///C:/…/out/renderer/index.html#/q')` gives `origin + pathname` = `null/C:/…/out/renderer/index.html`. That never equals the file URL `file:///C:/…/index.html`.
- In dev, `origin + pathname` gives `http://localhost:5173/`, with a trailing slash. A bare env URL does not have one.

Taken literally, every call fails in the packaged app. The easy "fix" is to loosen the check (pathname only, `startsWith`, or origin only, which is `"null"` for every `file:` page). That would weaken the only trust check on the IPC boundary.
Fix: compare normalized `href`s with the hash and query removed, using the same URL the window loads:
```ts
// electron/main.ts
const pageUrl = (s: string) => { const u = new URL(s); u.hash = ''; u.search = ''; return u.href }
const rendererUrl = pageUrl(dev ? process.env.ELECTRON_RENDERER_URL! : pathToFileURL(indexHtml).href) // window.loadURL(rendererUrl)
// in ipcMain.handle('call', …)
if (!e.senderFrame || pageUrl(e.senderFrame.url) !== rendererUrl) return { ok: false, status: 403, error: 'Not allowed' }
```
State the rejection status (403). The packaged smoke test (`test:app`, Login visible) proves the check passes.

### 2. MEDIUM: canceling a paused or queued download leaves its partial data, but the Clear All confirm says it is deleted
Where:
- ARCHITECTURE > Methods notes (`jobs.action`): "`pause` and `cancel` on a job with no live engine state … skip TDLib calls and only update or delete the row"
- Transfer engine: live state exists only for active jobs
- TDLib call map: "Download pause / cancel: … cancel also `deleteFile`"
- UI.md Queue > Clear All: "Remove all `<n>` jobs? Partial downloads are deleted."

Problem: paused, queued, failed, and crash-requeued downloads have no live state, so cancel skips `deleteFile`. Their TDLib partial data stays in `tdlib\files` until the user runs Clear cache. That can be gigabytes per canceled job. It happens through Queue Cancel/Remove, Clear All, the Overview row menu, and the Downloads card. The confirm text promises the opposite.
Fix: in `jobs.action cancel`, a download job that has been started (`attempts > 0`) and has no live state, while auth is `ready`, gets its partial data deleted best effort. Batch it with `getMessages`, 100 ids per call, as `downloads.add` does:
```ts
// per batch of started, non-live download jobs being canceled
const { messages } = await invoke({ _: 'getMessages', chat_id, message_ids })
for (const m of messages) { const f = m && extractMedia(m)?.file; if (f) await invoke({ _: 'deleteFile', file_id: f.id }).catch(() => {}) }
```
When Telegram is not ready, add `// ponytail: partial data stays until Clear cache; upgrade: retry on next ready`. Make the TDLib call map row say "cancel also `deleteFile` (non-live started downloads: `getMessages` first)".

### 3. MEDIUM: after a crash, pending upload ids can be routed to the wrong file, so a file is posted twice or never posted
Where: ARCHITECTURE > SQLite schema (`jobs.pending`: "JSON [temporary message id] while sending"); Upload steps 3, 4, and 6 (`Map<tempMessageId, { jobId, index }>`, "loads every active upload's `pending` ids into the routing map").
Problem: `pending` stores only ids. The `index` into `files` cannot be recovered from it after any file of the send has succeeded. An example:
1. Files f1, f2, and f3 are sent as t1, t2, and t3.
2. t1 succeeds, and `files[1].messageId` is persisted. `pending` is still `[t1, t2, t3]`.
3. The app crashes.
4. On restart, the unsent files are f2 and f3, but there are three pending ids. Positional mapping shifts, so t2's success marks the wrong file as sent.

The file that really went out has no `messageId`, so Retry posts it again. The file that was wrongly marked is never sent, but the job completes and history records it as uploaded. This breaks the invariant "An upload file is posted at most once", and it silently drops a user's file.
Fix: keep the temporary id on the file entry and delete the `pending` column, which follows Ponytail's "deletion over addition":
```ts
// jobs.files: [{ path, name, size, type, pendingId?: number, messageId?: number }]
// send:    files[i].pendingId = tempId (persist files)
// settle:  success → messageId = new id, delete pendingId; failure → delete pendingId
// startup: for each active upload, for each file with pendingId && !messageId → route.set(pendingId, { jobId, index: i })
```
Update Upload steps 3, 4, and 6, the schema comment, and the "Upload crash recovery" row. Extend the `settleUpload` test: after a restart with `files[1].messageId` set and `files[2].pendingId` set, a success for `files[2].pendingId` marks index 2.

### 4. MEDIUM: quitting or crashing during a cross-volume finalize leaves a truncated file under the final name
Where: ARCHITECTURE > Download step 6 (`fs.rename`; on `EXDEV` copy then delete; a failed copy removes the partial destination); Quit ("Active downloads are left as they are").
Problem: the cleanup covers only a copy that throws. Quit does not wait for in-flight finalizes, and a crash cannot wait at all. If either happens during a multi-GB copy to another drive (for example a `D:\Media` root), the file under its final name is truncated. On the next start:
1. The job is requeued, but step 4 does not match because the size differs.
2. TDLib still has the complete file, so `deleteFile` was never called.
3. Finalize picks ` (2)`.

The truncated file stays in the Library as a real download, which is the data-integrity case the round-2 #6 fix was aiming at.
Fix: copy to a dot-prefixed temp name in the target folder, then rename it on the same volume. The Library scan already skips dot-prefixed entries.
```ts
// EXDEV branch of finalize
const part = path.join(dir, `.teleflow-${job.id}.part`)
await fs.promises.rm(part, { force: true })                       // stale part from an interrupted run
try { await fs.promises.copyFile(src, part); await fs.promises.rename(part, dest) }
catch (e) { await fs.promises.rm(part, { force: true }); throw e }
await fs.promises.rm(src)
```
Add `// ponytail: a part file of a job canceled after a crash is not swept; upgrade: sweep .teleflow-*.part on Clear cache`. Same-volume moves stay a single `fs.rename`.

### 5. MEDIUM: a skip-existing completion does not say it writes history, which breaks dedupe after Clear Completed
Where: ARCHITECTURE > Download step 4 ("`skipExisting` and a file with that name and the expected size exists → completed with that path, no transfer"). Only finalize (step 6) says "Update the job … and insert history in one transaction".
Problem: `MediaItem.status = downloaded`, `missing`, Library metadata, and the stats all read `history`, and dedupe without `force` relies on that status. If step 4 only updates the job row, Clear Completed or `clearCompletedDays` turns every skip-completed item back to "Not downloaded". This hits FileGram-moved files in particular. "Download all matching" then reports them as "Added" and runs them through the queue again. Round 1 #5 ("dedupe holds after Clear Completed") fails for exactly this path.
Fix: step 4 completes through the same `complete(job, path)` transaction as finalize: job `completed` + `path` + `finished_at`, one `history` row, the thumbnail save, and the same invalidations. It skips the move, Mark-of-the-Web, and `deleteFile`. Add a test: after a skip completion and Clear Completed, `MediaItem.status` is still `downloaded`, and `downloads.add` counts the item in `skipped`.

### 6. MEDIUM: `scans.newest_id` is ambiguous, and the natural reading re-starts a scan on every refetch
Where: ARCHITECTURE > SQLite schema (`newest_id INTEGER NOT NULL, -- newest message id indexed`); Media index scan ("starts a scan … when … its newest indexed id is older than the chat's last message").
Problem: "newest message id indexed" reads as the newest media message. In a chat whose last message is text, that id is always older than the last message. As a result:
- every `chats.media` call starts a top-up, and `scan.state` flips to `scanning`, so the index bar flickers;
- every download status change in that chat triggers a `media:<chatId>` refetch, which starts the next top-up;
- the scan has to emit `media:` when it finishes so the bar hides, so this becomes a refetch → scan → invalidate loop with TDLib calls about once per second for as long as Files View is open.

Fix: define the fields by messages walked, not media indexed:
- `newest_id` = id of the newest message the walk has seen (any content).
- `oldest_id` = id of the oldest message seen.
- Live upkeep sets `newest_id = max(newest_id, message.id)` for every `updateNewMessage` in a chat with a `scans` row, media or not.
- The start condition compares against `chat.last_message.id`.
- Emit `media:<chatId>` when `scan.state` changes (start and finish), so the index bar hides. With the fixed fields this cannot loop.

### 7. NIT: `supports_streaming` belongs to `inputVideo`, not `inputMessageVideo`
Where: Upload step 3 (`inputMessageVideo { video: inputVideo, supports_streaming }`).
Problem: in 1.8.66, `supports_streaming` is a field of `inputVideo`, which I checked. Put on the outer object, it is ignored, and videos post as not streamable.
Fix: `{ _: 'inputMessageVideo', video: { _: 'inputVideo', video: inputFileLocal, supports_streaming: true }, caption }`.

### 8. NIT: failed album messages must be deleted by their new id
Where: Upload step 4 ("Any failed → delete the failed local messages").
Problem: `updateMessageSendFailed` carries `message` (the failed message, with its own id) and `old_message_id` (the temporary id), which I checked. Deleting by the temporary id leaves the failed local message in the chat.
Fix: "delete `update.message.id` with `deleteMessages(chat_id, [ids], revoke: true)`". Pause and cancel keep using the temporary ids of messages that are still pending.

### 9. NIT: TDLib-to-shape mappings are unstated
Where: Shared shapes and Chat cache.
Fix: add one line for each:
- `Folder.name` = `chatFolderInfo.name.text.text`. In 1.8.66 `name` is a `chatFolderName` object, not a string (checked).
- `Chat.photo` = `chat.photo.small.remote.id`, and `Me.photo` = `user.profile_photo.small.remote.id`.
- `AuthState.connection` comes from `updateConnectionState`:
  - `connectionStateReady` → `ready`
  - `Updating` → `updating`
  - `Connecting` and `ConnectingToProxy` → `connecting`
  - `WaitingForNetwork` → `offline`
  - `offline` also applies while no client exists
- `fileGram.import` `session` is a `boolean` (true when the session was moved).

### 10. NIT: `ids` up to 50 000 exceeds SQLite's bound-parameter limit
Where: `jobs.action` `ids?: id[] (1–50000)`.
Problem: `node:sqlite` fails at 32 767 bound parameters with "too many SQL variables" (checked). An `IN (?, ?, …)` list over that size becomes a 500.
Fix: `WHERE id IN (SELECT value FROM json_each(?))` with `JSON.stringify(ids)`. I checked this with 50 000 ids. The other option is to cap `ids` at 1000, since selections are per page.

### 11. NIT: electron-builder may try to rebuild `tdl` from source
Where: Build > electron-builder config.
Problem: `tdl` 8.1.0 ships `binding.gyp` and an `install: node-gyp-build` script next to `prebuilds/win32-x64/tdl.node` (checked). electron-builder's default `npmRebuild: true` can invoke `@electron/rebuild`. That would need Python and MSVC on the build machine and in CI. The N-API prebuild already loads in Electron 44 (PROGRESS spike), so no rebuild is needed.
Fix: add `"npmRebuild": false` to the `build` config. Confirm in the Phase 1 packaging spike.

### 12. NIT: "Show in folder" returns 404 for downloads made before a download root change
Where: Methods notes (`library.*` paths "must be inside the root"); Queue and Chat View reuse `library.reveal` with `job.path` and `media.path`.
Problem: changing the root does not move files, and history keeps their absolute paths, so those items still show "Downloaded". Their "Show in folder" and "Open" then fail with 404.
Fix: accept a path that is inside the root, or one that equals a completed download's `jobs.path` or `history.path`. The files stay confined to ones TeleFlow wrote. Also state in Settings > Download folder: "Existing downloads stay where they are".

### 13. NIT: topic table gaps
Where: Events > Who emits which topic; Settings keys.
Problems and fixes:
- The `downloadRoot` row says it invalidates `storage`, but the `storage` topic row omits it. Add "download root change".
- Window move and resize writes to the `window` setting should not emit `settings`. Otherwise Settings refetches while the window is dragged. State it.

### 14. NIT: history row granularity is inconsistent
Where: the schema comment on `history` says "one row per file", but the engine says "A final failure inserts one history row".
Fix: "completed: one row per file; failed: one row per job (`name` = job name)".

### 15. NIT: Files View details while indexing
Where: `chats.media` `exts`; UI.md Downloads > File rows Empty.
Fixes:
- `exts` = the distinct `ext` values of the whole chat index, ignoring filters, so the File Type options do not collapse to the selected value.
- When `scan.state === 'scanning'` and there are no rows, show the index bar and skeleton rows, not "No media in this chat".

### 16. NIT: partial resolution in `downloads.add` is unspecified
Where: `downloads.add` Errors ("400 no media, 404, 503").
Problem: for `items` or Verify re-downloads, it is unclear what happens when some messages are gone, have no media, or `getMessages` returns `null` for them.
Fix: "Unresolvable items count as `skipped`. 404 only for an unknown chat. 400 'no media' only for `{ link }`."

### 17. NIT: the login item outlives Clear All Data and uninstall
Where: Storage > Clear All Data; Build > NSIS.
Problem: Clear All Data leaves Start with Windows on. The NSIS uninstaller does not remove the `HKCU\…\Run` value that `setLoginItemSettings` wrote (value name = AppUserModelId `com.teleflow.app`), so Windows keeps a dead startup entry.
Fix:
- Clear All Data calls `app.setLoginItemSettings({ ...loginItem, openAtLogin: false })`.
- Add `assets/installer.nsh` with a `customUnInstall` macro: `DeleteRegValue HKCU "Software\Microsoft\Windows\CurrentVersion\Run" "com.teleflow.app"`. Confirm the value name in Phase 6.

### 18. NIT: trash matches `lower(path)` without an index
Where: the `library.trash` note: `UPDATE history … WHERE kind = 'download' AND lower(path) = lower(?)`, plus the matching delete on `jobs`.
Problem: each trashed file causes a full scan of `history` and `jobs`, and a 1000-file trash repeats that 1000 times.
Fix: add `CREATE INDEX history_path ON history (lower(path))` and `CREATE INDEX jobs_path ON jobs (lower(path))`. SQLite uses expression indexes for this predicate (checked with `EXPLAIN QUERY PLAN`).

### 19. NIT: what logout does to the queue is unstated
Where: Client lifecycle (leaving `ready`); PRODUCT Log out.
Problem: jobs survive logout. If a different account signs in, they run under that account and fail as "This message no longer exists", or as "Interrupted" for uploads.
Fix: state it with `// ponytail: jobs are not tied to an account; upgrade: store me.id on jobs and pause other accounts' jobs`. That costs no code.

### 20. NIT: how `position` is assigned is unspecified
Where: schema (`position … starts as id`); enqueue upsert.
Problem:
- One `INSERT` cannot read its own new id.
- The upsert keeps a failed job's old `position`, so retried jobs run before newer ones. It is unclear whether that is intended.

Fix: specify `position = (SELECT IFNULL(MAX(position), 0) + 1 FROM jobs)` in the insert, or an `UPDATE … SET position = id` in the same transaction. Then state the retry order: either "retry keeps its place", or the upsert also sets `position` to the new maximum.

### 21. NIT: unused shape fields
Where: `Chat.archived`, `Message.outgoing`, `Job.fileCount`, `Job.attempts`, `Job.createdAt`.
Problem: UI.md binds none of them. `archived` is needed only for server-side ordering.
Fix: drop them from the shapes, or bind them. For example, Chat View could align outgoing messages, and upload cards could show "`<fileCount>` files".
