### Real-location check compares resolved roots to unresolved lists

`settings.set` now runs the rules twice:

```ts
next.downloadRoot = checkDownloadRoot(next.downloadRoot, ctx.roots)
checkDownloadRoot(await realLocation(next.downloadRoot), ctx.roots) // the stored path stays the one picked
```

`ctx.roots` comes from `main.ts` unchanged: `paths.home`, `paths.appDir`, `path.dirname(app.getPath('appData'))`, the system env folders, and `app.getPath` for home and the six known folders. None of them goes through `realpath`, so the two comparisons are path vs raw list and real vs raw list. A protected folder whose registered path is a junction is matched only by that junction path:

```
app.getPath('documents') = C:\Users\u\Documents   (junction → D:\Docs, a common way to move profile folders)
user picks D:\Docs
  path check:  D:\Docs vs C:\Users\u\Documents  → passes
  real check:  realLocation(D:\Docs) = D:\Docs   → passes   (D:\Docs is never in the list)
→ the Library lists Documents; 3.6's "Also delete downloaded files" would empty it
```

The known-folder API keeps returning `%USERPROFILE%\Documents` when that folder was replaced by a junction (the registry path is unchanged), so user setup alone reaches this (confirmed in code; likely for users who relocate folders that way). The same asymmetry applies to `TELEFLOW_HOME` or a custom install folder reached through a junction or an 8.3 short path. The default layout is covered only because the `AppData` seal is a long real path and both home and the default install folder sit under it.

The new `settings.set` junction test hides this. It realpaths the lists before calling (`f.ctx.roots = { sealed: [fs.realpathSync.native(f.paths.home)], guarded: [fs.realpathSync.native(docs)] } // main's lists are real paths`), but main never builds them that way. Listing each entry as both `p` and its `fs.realpathSync.native(p)` (falling back to `p` when that throws) once at startup closes the gap, and a test whose guarded entry is the junction path, rejecting its target, would pin it.

### Save-time check versus the 3.6 delete

The real-location rule is enforced at one point: when `settings.set` receives a `downloadRoot`. Two roots never reach that point. The default root (`app.getPath('downloads')\TeleFlow`) is returned by `getSettings` without being stored or checked, and a root that was a plain folder or a harmless junction when saved can later be replaced by a junction into a protected folder. The ARCHITECTURE wording ("so a junction such as `D:\Media` → `Documents` gets the same 400") holds only at save time. Review 1 offered "re-check in `settings.set`, or make 3.6 delete only through the real path"; the first half is done, and the second is still needed because Clear All Data's delete is the one action that turns a bad root into data loss. Running `checkDownloadRoot(await realLocation(root), roots)` at the top of that delete and refusing on a 400 is enough (confirmed; Phase 3 item 3.6).

### Telegram module: what the fake client does not reach

Not tested: `openChat` invite handling (the `invite` preview, the 409 for a sent join request, the 403 for declined or guard-bot results, `opened` membership after a successful join), `thumbFile`'s size cap (the 413 must come before any `downloadFile`, which keeps `teleflow://thumb` from fetching large files), the `updateOption` caption refresh and the `updateUser` premium change on `me`, and `linkType`'s 404 → 400 mapping at the module level. With the fake in place each is a few lines. The fake proves the module's branches, not TDLib's real update order; that stays with the manual login check, as PROGRESS records.
