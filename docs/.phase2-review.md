# Phase 2 core: SQLite, settings, Library, TDLib client and auth, 21 IPC methods

Phase 2 (commit `eaee7cb5`, items 2.1–2.4) builds the main-process core of TeleFlow. `core/db.ts` gets schema v1 and settings, and `core/storage.ts` gets the download-root rules, the Library, trash, and the storage report. `core/shapes.ts` holds the pure TDLib mappings, and `core/telegram.ts` holds the stateful TDLib singleton (lifecycle, auth, chat cache, links, messages, thumbnails). `electron/ipc.ts` has 21 of the 33 IPC methods plus the `teleflow://` resolver, and `electron/main.ts` runs the full startup and quit sequence. Several checks pass:

- The schema and settings match ARCHITECTURE.
- Runtime data resolves outside the repo and the install folder, under `TELEFLOW_HOME` or else `%LOCALAPPDATA%\TeleFlow` (`TeleFlow-dev` in dev).
- Downloads default to `%USERPROFILE%\Downloads\TeleFlow`.
- The hardcode, pin, and data gates are clean, and the docs are current.

The weak spot is `core/telegram.ts`. It has no runnable check, and it merges chat positions in a way that does not match how TDLib sends updates.

Watch for: `core/telegram.ts` lifecycle, chat cache, and message paging have no test, although they can be tested today with no code change (blocking, confirmed). `updateChatLastMessage`/`updateChatDraftMessage` positions are merged per list instead of replaced (likely). `start()` is not serialized, so two overlapping starts can orphan a TDLib client (likely). `app.storage` returns a 500 when the download root's drive is gone (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The download root rules protect the right folders but compare paths only. `checkDownloadRoot` seals `home`, `appDir`, `AppData`, and the system folders, and guards the profile and known folders. It never resolves the filesystem, so a junction or symlink that points into Documents or AppData passes. That matters once Clear All Data's "delete downloads" lands in 3.6.

`storageReport` is all-or-nothing. If `statfs` fails because the root's drive is gone, the whole report is a 500, cache sizes included.

The Telegram layer follows ARCHITECTURE, with two deviations recorded in the Decision log: the session is deleted only after `LoggingOut`, and `ChatJoinResult` is handled. Three gaps remain. Chat positions from last-message and draft updates are merged when TDLib means them to replace the old ones. `start()` can interleave with itself while the previous client is closing. None of the stateful module's branches has a runnable check.

IPC holds the trust boundary: the sender check runs first, methods are looked up as own properties, and every field is validated with a 400 that names it and never echoes the value. Moving `protocolFile` into `ipc.ts` gave the `teleflow://` confinement a `node:test` check. One gap: `shell.openPath` failures (for example "no app associated") come back as a generic 500 instead of a readable message.

The requested checks are clean:

- The hardcode grep over `electron/`, `core/`, and `web/src/` prints nothing.
- `package.json` has no `^` or `~` pins.
- `git status --short --ignored` lists only build output.
- The four docs match the main-workspace mirror.
- The five `ponytail:` comments match the Changelog.

The recorded evidence covers typecheck, 41/41 tests, build, dist with no node-gyp lines, and test:app. Phase 1 review items #1–#4 and #6 are resolved, and #5 is deferred to Phase 6.

### Chat cache positions diverge from TDLib's update semantics

The TDLib 1.8.66 types document `updateChatLastMessage.positions` and `updateChatDraftMessage.positions` as "The new chat positions in the chat lists". `updateChatPosition` adds that "An updateChatLastMessage or updateChatDraftMessage update might be sent instead of the update". So a chat can leave a list through a last-message update whose `positions` vector no longer contains that list. TDLib's reference client replaces `chat.positions` wholesale for those two updates and merges per list only for `updateChatPosition`. `core/telegram.ts` merges for all three:

```ts
function setPositions(c: Td.chat, positions: Td.chatPosition[]) {
  for (const p of positions) {
    c.positions = c.positions.filter((x) => !sameList(x.list, p.list))
    if (p.order !== '0') c.positions.push(p)
  }
}
case 'updateChatLastMessage': patch(u.chat_id, (c) => { c.last_message = u.last_message; setPositions(c, u.positions) }); break
case 'updateChatDraftMessage': patch(u.chat_id, (c) => setPositions(c, u.positions)); break
```

When the vector omits `chatListMain`, the old main position stays, so `chatList()` keeps listing the chat and sorts it by the old `order` until restart (likely). The fix for those two updates is `c.positions = u.positions`, with `setPositions` kept for `updateChatPosition`.

### telegram.ts has no runnable check

All tests in `tests/shapes.test.ts` cover pure helpers. None of the stateful module's branches is checked:

- `onClosed` decides whether to delete `tdlib\db` (only after `LoggingOut`) and restarts with the same credentials. If this branch is wrong, the app either signs the user out after a TDLib crash or keeps a session after logout.
- `rejectCredentials` is reached from both the `error` event and a failing `setAuthenticationPhoneNumber`. It must close the client, forget the stored credentials, and show the credentials step with the reason.
- The `invoke` 503 gate holds until `me` is loaded, and `onReady` decides when the step becomes `ready`.
- `chatList()` sets membership (main list, the archive only when shown, Saved Messages, the opened set) and order.
- `messages()` pages by 100 and computes `more`.
- `logout()` falls back to a local delete after 15 s.

The changelog marks these "Not verified (no Telegram account)", and agents never run the manual login check. A fake-client test is the only automated evidence they can get before Phases 4–5 build Login and Downloads on them.

No production seam is needed. `tdl` exports `createClient` as a plain writable property (`node_modules/tdl/dist/index.js:44`, `exports.createClient = createClient`), and `telegram.ts` calls it as `tdl.createClient(...)`. A test can assign a fake: an `EventEmitter` whose `invoke(req)` answers from a table and whose `close()` emits `close`. The test then drives `update` events and asserts on `authState()`, `chatList()`, `messages()`, and whether `tdlib\db` under a `mkdtemp` folder still exists.

Ponytail requires a runnable check for non-trivial branches and loops, and the session-deletion branch protects user data. That makes this the blocking item (confirmed).

### `start()` and `close()` can interleave

`start()` awaits `close()`, which sets `client = null` before it awaits the old client's shutdown (up to 5 s). A second `start()` that begins in that window sees no client, skips the close, and creates client B. When the first `start()` resumes, it creates client A and overwrites `client` without closing B:

```
start#1: close() → client = null, awaiting X.close() ……………… → createClient → client = A
start#2:            close() sees null → createClient → client = B   (B never closed)
```

B's events are ignored (`client !== cl`), but B keeps TDLib's lock on `tdlib\db`, so A cannot open the database. The trigger is two `auth.credentials` calls while a client exists, for example a double-submit after going Back from the phone step (likely; needs overlapping calls). Phase 4's busy buttons would make this rarer, but the fix belongs in the module: loop `while (client) await close()`, or chain `start` and `close` through one promise.

### Download root and storage edge cases

`checkDownloadRoot` uses only `path.resolve`. So a root such as `D:\Media` that is a junction to `C:\Users\u\Documents` passes both lists, and the Library scan reads the root through the junction. Clear All Data with "Also delete downloaded files" (3.6) deletes every file the Library lists. The check is confirmed; the deletion path lands in Phase 3. `settings.set` already creates the folder, so it can re-run the check on `fs.promises.realpath(root)` right after `mkdir`.

`storageReport` runs `fs.promises.statfs(path.parse(root).root)` in the same `Promise.all` as the cache and app-data sizes. With the root on a removable or disconnected drive (a second-drive manual check is planned), `app.storage` is a 500. Settings then loses the drive bar, the App cache size, and the Clear cache / Clear app data sizes (confirmed).

### Test coverage

The 41 `node:test` cases cover every case the plan lists for 2.1–2.4, including junction escapes for both `libraryFile` and `teleflow://image` and a check that no 400 echoes the API hash. The fixtures use made-up values (`9.9.9`, `Fixture chat`), and every temp folder comes from `mkdtemp` and is deleted afterwards.

Not tested: everything in `core/telegram.ts` (Issue 1), the `invalidate` coalescing timers and the window-state restore in `main.ts`, `settings.set` with `showArchived` triggering `loadLists`, and the `freed` value from `auth.logout`.
